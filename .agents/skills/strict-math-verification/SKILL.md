# Strict Math Verification & Benchmarking

Use this skill whenever you are tasked with verifying a mathematical claim, evaluating a formal proof, or benchmarking hardware code (e.g., PyTorch/Triton kernels) within the SocrateAI project.

## Mathematical Proofs

1. **Never Trust 'Completed' Status Without Logs**: If a script reports that a proof is completed, you MUST verify the underlying Lean file for the presence of `sorry`. Use `grep_search` to ensure `sorry` is entirely absent.
2. **Require `lake build`**: A proof is not valid until you successfully run `lake build` from the project root and the compiler emits no errors.
3. **No `sorry` in Definitions**: A `sorry` inside a definition (e.g., `def fanoSeq ... := sorry`) will vacuously solve any dependent theorem. You must ensure all definitions are fully concrete or `axiom` bounds.
4. **LLM != Truth**: Never use LLM consensus to evaluate mathematical novelty or truth. Use exact symbolic arithmetic (SageMath/Python exact) for numerical falsification, and Lean 4 for formal proof.
5. **No Circular Constants**: Never accept a Lean 4 theorem as physically meaningful if its conclusion is forced by a circularly-constructed constant (e.g., `K_heating` defined as `f(m)` then used to prove `K_heating/m³ > threshold`).
6. **Physically Relevant Derivatives**: Verify that `HasDerivAt` proofs correspond to physically relevant derivatives, not trivial calculus identities disconnected from the claimed physics.
7. **Never hardcode a "known" integer sequence as a literal array.** Found 2026-07-15: `COOPER_S7_EXACT` in `cooper_s7_periods.py` was a fabricated array (satisfied neither the Lean-verified recurrence nor OEIS A183204) that silently invalidated a prior session's headline "discovery" statistic. Any sequence claimed to match a Lean recurrence or an OEIS entry MUST be **computed** from its combinatorial/recursive definition in the same script (arbitrary-precision integers), with a self-check at import/run time that (a) the committed recurrence evaluates to zero on the computed terms, and (b) if an OEIS number is cited, the terms match a fetched b-file (`curl -A "Mozilla/5.0" https://oeis.org/A#/b#.txt`, since default WebFetch gets 403'd by OEIS — use Bash/curl instead). A hand-typed array is a claim with no verification attached; treat it as false until it self-checks.
8. **Verify symbolic operator translations by independent substitution, not internal consistency alone.** A recurrence-to-ODE (or any operator-algebra) derivation can be internally consistent yet still wrong (e.g., forgetting an index-shift correction like `P_k(theta - k)` vs `P_k(theta)` when re-indexing `a(n+k)`). Before trusting a derived operator/ODE, substitute the actual truncated series (exact integers) into it and confirm the coefficients vanish out to a safe truncation window — this caught a real shift-indexing bug in the first attempt at the GATE D-2.4 singular-locus derivation (2026-07-15), where the leading coefficient came out right by coincidence but the lower-order terms did not.

## Hardware & Performance Benchmarking

1. **Zero Empirical Claims Without Execution**: Do not report VRAM savings, FLOP improvements, or accuracy metrics without executing the benchmark script on the target hardware.
2. **Execute First**: If asked to assess a kernel's performance, provision or execute the benchmark code (e.g., `run_full_benchmark.py`) first. If you cannot access the required hardware (e.g., GPU), state honestly: "Hardware execution pending. No empirical claims can be made."
3. **Inspect Output Files**: Always inspect the physical JSON or text logs generated by benchmark orchestrators to confirm the numbers before reporting them.
4. **Physically Motivated Initial Conditions**: For cosmological solvers, verify that the ODE initial conditions are physically motivated (e.g., tracker attractor for quintessence), not default zeros.

## Handling Failures

If a proof fails or a benchmark produces an error, report the precise error directly to the user. Do not attempt to mask the error by simulating a success state or generating a plausible-sounding excuse.
