# SocrateAI Workspace Rules

These rules apply strictly to all agents operating within the SocrateAI-Scientific-Agora workspace to enforce mathematical and empirical rigor.

## Rule 1: The 'No Simulation' Rule
**Never report benchmark or performance metrics without hard execution data.**
- Do not rely on simulated logs, placeholder JSONs, or speculative results.
- Any claim regarding speedups, memory savings, or accuracy (e.g., MMLU, GSM8K, hardware latency) MUST be backed by an execution log from the target hardware (e.g., GCP A100/T4 VMs).
- If execution data is absent, state clearly: "Pending hardware verification."

## Rule 2: The 'Strict Formalization' Rule
**Never consider a mathematical theorem 'proven' unless verified by the Lean 4 kernel.**
- Do not accept claims based solely on Python `assert` tests or symbolic algebra execution.
- A proof is only valid if it compiles under `lake build` with zero `sorry` stubs and zero unverified axioms.
- Do NOT use `sorry` in any definition or lemma to force a build to succeed. Doing so vacuously proves all downstream dependencies and completely voids the proof's validity.

## Rule 3: The 'No LLM Peer Review for Math' Rule
**Do not use LLMs as the final arbiter of mathematical truth.**
- Mathematical correctness is determined by formal logic systems (e.g., Lean 4), not LLM consensus.
- While LLMs can generate hypotheses or suggest steps, they must never be used to definitively state that a conjecture is true or false.
- Treat LLM outputs as strictly unverified drafts until proven otherwise by a kernel.

## Rule 4: The 'Adversarial Assessment' Rule
**Evaluate all outputs with extreme skepticism.**
- Avoid self-congratulatory AI feedback loops. Do not claim a result is a "breakthrough" unless explicitly instructed by a human supervisor or confirmed by independent external publication.
- Assume all LLM-generated code contains bugs and all LLM-generated math contains hallucinations until proven otherwise.

## Rule 5: The 'Exact Sequence Generation' Rule
**Never extract mathematical sequences from simulated or stubbed outputs.**
- Agents are strictly prohibited from hallucinating, guessing, or using simple `eval()` stubs to generate physical sequences.
- Any sequence passed to exact solvers MUST be generated by a physically executed script (e.g., exact SymPy Taylor expansion, `rusty-SUNDIALS` integration) producing verifiable execution logs.
- If the exact algebraic coefficients cannot be generated by actual code, the agent must abort the sequence mining attempt.

## Rule 6: The 'Atomic Caveat Propagation' Rule
**Caveats documented in CAVEATS_K3.md or equivalent MUST simultaneously appear in every manuscript and public document that makes the corresponding claim.**
- A caveat that exists only in an internal file is operationally invisible.
- Every release or major update must verify that limitations are openly acknowledged in manuscripts.

## Rule 7: The 'No Circular Derivation' Rule
**Never fit input parameters to reproduce a pre-assumed output and call it a "derivation."**
- If a parameter $\tau$ is found by minimizing $|m_a(\tau) - m_{\text{target}}|$, state clearly that this is a parameter fit, not a first-principles prediction.

## Rule 8: The 'Cross-Consistency Gate' Rule
**Before any release tag, every numerical value (e.g., $(w_0, w_a)$, $H_0$, $\lambda$, GD-1 bound) must be verified to be identical across all code, benchmark JSONs, and manuscript text.**
- Discrepancies are release-blocking.
